# Audit de sécurité — 25 juillet 2026

Portée : tout le projet — backend (`src/`, 20 modules), frontend (`public/`,
9 scripts), robots Playwright (BlueKanGo, NetSoins), système de licence,
dépendances. Périmètre fonctionnel : SSO Microsoft 365, habilitations par
établissement, 5 démarches, remise des identifiants, panel d'administration.

**Méthode** : aucune conclusion n'a été tirée par lecture seule. Chaque
hypothèse de faille a été jouée contre un serveur réel (scénarios rejouables,
section « Tests »), et chaque correction a été re-testée après application.

## FAILLE ÉLEVÉE — Un référent pouvait prendre le contrôle de l'application métier

### Ce qui était possible

Le robot se connecte à BlueKanGo et à NetSoins avec un compte
**administrateur** (`BLUEKANGO_ADMIN_USER`, `NETSOINS_ADMIN_USER`). Rien
n'empêchait un référent de déposer une démarche **visant ce compte** :

1. « Mot de passe oublié » sur `amaatoug` (l'administrateur BlueKanGo) ;
2. le robot, connecté avec ce compte, lui attribue un mot de passe provisoire ;
3. ce mot de passe est remis **au demandeur** par lien sécurisé.

Le référent devenait administrateur de BlueKanGo — donc de tous les
établissements du groupe, bien au-delà de son périmètre. Variantes tout aussi
efficaces : renommer le compte de service (plus aucun robot ne se connecte),
le transférer d'établissement, ou renommer un compte quelconque **vers**
l'identifiant de l'administrateur.

Vérifié avant correction : les 6 tentatives passaient, HTTP 201.

### Correction

Nouveau module `src/comptesProteges.js`. Les comptes de service (compte
d'administration de l'application + liste facultative
`<APP>_PROTECTED_LOGINS`) sont refusés :

- **au dépôt** (`POST /api/apps/:id/requests`) : 403 et journalisation
  `depot_refuse_compte_protege` ;
- **dans les robots** (6 actions concernées) : la demande échoue avec un
  message explicite, y compris pour une demande insérée directement en base ou
  déposée avant la mise en place du contrôle.

La comparaison ignore la casse, les accents et les espaces multiples
(`amaatoug`, `AMAATOUG`, `Amaatoug ` sont un seul et même compte), et couvre
les deux formats d'identifiant en usage (`1re lettre du prénom + nom` pour
BlueKanGo, `NOM PRÉNOM` pour NetSoins).

**À faire côté exploitation** : renseigner
`BLUEKANGO_PROTECTED_LOGINS` / `NETSOINS_PROTECTED_LOGINS` avec les éventuels
autres comptes techniques du client (interfaces, exports, comptes de test).

## FAILLE MOYENNE — Fuite de données personnelles par référence de suivi

### Ce qui était possible

`GET /api/requests/:reference` renvoyait le détail d'une demande à **tout
compte Microsoft du tenant**, sans vérifier qu'il était concerné. Le message
de résultat contient le nom du bénéficiaire, son identifiant de connexion et
son établissement :

> `Compte créé pour Marie DUPONT — identifiant « MARTIN PAUL », établissement EHPAD MON FOYER`

Les références sont courtes (`PREFIXE-AAMMJJ-XXXX`, 4 caractères aléatoires) :
en essayant des références, un salarié quelconque pouvait moissonner des noms
et des identifiants de connexion. Le quota (120 requêtes / 10 min) ralentit
sans empêcher.

Vérifié avant correction : HTTP 200 avec le message complet.

### Correction

La lecture est réservée aux personnes concernées : le déposant (compte
Microsoft du dépôt), le bénéficiaire (e-mail de la demande), un référent de
l'établissement visé (départ **ou** arrivée pour un transfert), ou un
administrateur connecté au panel. Sinon **404** — la même réponse qu'une
référence inconnue, pour ne pas confirmer l'existence de la demande. Refus
journalisé (`suivi_refuse`).

## FAILLES FAIBLES

### 1. Ordre des contrôles sur la remise des identifiants

`POST /api/requests/:reference/credentials-access` vérifiait l'état de la
demande **avant** l'habilitation : un tiers recevait 409 (« pas encore créé »)
ou 200, ce qui renseignait sur l'existence de la demande et sur la présence
d'un mot de passe à récupérer. L'habilitation passe maintenant en premier, et
répond 404 pour un tiers.

### 2. Un lien d'identifiants pouvait annoncer un mot de passe erroné

Une correction d'identité ne change pas le mot de passe. Le bouton
« Récupérer les identifiants » régénérait pourtant un lien, avec le mot de
passe **initial** de l'application — un mot de passe qui n'est pas celui du
compte. Corrigé : le lien n'existe que si un mot de passe a réellement été
posé (création, réinitialisation) ; l'API refuse sinon (409), et le bouton
disparaît de la page de suivi.

### 3. Fichiers de données lisibles par tous les comptes du serveur

`data/portail.db` était créé en `0644` : tout compte local pouvait lire les
données personnelles et les secrets chiffrés. La base, ses fichiers WAL et les
dossiers de données/captures sont désormais restreints (`0600` / `0700`) au
démarrage, sans faire échouer le portail sur un système de fichiers sans
permissions POSIX.

Points de conception vérifiés au passage :

- **SSO** : `state`, PKCE, `nonce`, `aud`, `iss`, `tid` (annuaire) et `exp` sont
  tous contrôlés ; le jeton Microsoft ne transite jamais par le navigateur ; le
  paramètre `next` est borné aux chemins internes (pas de redirection ouverte).
- **Mots de passe d'administration** : scrypt + comparaison à temps constant,
  hachage factice pour les comptes inconnus (pas d'oracle de temps), 8
  caractères minimum.
- **Liens d'identifiants** : jeton de 32 octets, haché en base, secret chiffré
  en AES-256-GCM avec une clé en `0600`, usage unique, révocation, expiration.
- **Porte SSO « fermée par défaut »** : toute route ajoutée est protégée sans
  action supplémentaire ; la liste des exceptions est explicite et courte.

## Recommandations (non appliquées — décisions d'exploitation)

1. **Durée de conservation.** Les captures d'écran des robots
   (`data/artifacts/`) montrent des fiches d'applications métiers : elles
   contiennent des données personnelles. Rien ne les purge aujourd'hui. Fixer
   une durée (90 jours ?) et purger, ainsi que les demandes closes anciennes.
   C'est une décision RGPD, elle vous revient : dites-moi la durée et
   j'implémente la purge.
2. **Deuxième facteur sur le panel d'administration.** L'accès admin donne
   accès à tout le portail. Le SSO Microsoft en second rideau (ou un TOTP)
   serait cohérent avec les droits que ce compte porte.
3. **HTTPS obligatoire + `ADMIN_COOKIE_SECURE=true` / `COOKIE_SECURE=true`.**
   Le panel le signale déjà en alerte quand ce n'est pas le cas ; à traiter à
   la mise en production (reverse proxy + certificat).
4. **`ADMIN_COOKIE_SAMESITE=None`** est possible par configuration (frontend
   sur un autre domaine). Cela affaiblit la protection CSRF : à n'utiliser que
   si un frontend distinct l'exige réellement.
5. **`style-src 'unsafe-inline'`** reste nécessaire (styles en ligne dans les
   pages). Sans conséquence directe tant que `script-src` reste strict, mais à
   nettoyer si l'on veut une CSP irréprochable.
6. **Sauvegarde de `data/`** (base + `secret.key`). Sans `secret.key`, les
   secrets chiffrés des liens d'identifiants sont irrécupérables. À inclure
   dans la sauvegarde, avec les mêmes protections que la base.

### Sur le système de licence

C'est un verrou **commercial**, pas un DRM : qui modifie le code source livré
peut désactiver n'importe quel contrôle local. Ce qui est garanti, et vérifié :
un client ne prolonge pas sa licence en éditant un fichier, une date, une clé
ou l'horloge du serveur. Détails et limites dans la documentation de licence conservée avec les outils de l’éditeur.
